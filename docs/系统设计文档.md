## 1. 系统定位

GXLF 集中管控系统（JZGK）是高功率激光聚变装置的控制软件核心。它的职责是将一次"发次"（shot）从操作员指令转化为协调16个子系统的具体动作序列，并在过程中监控安全状态、处理各类故障，最终收集实验数据并驱动模型校准。

系统面对的核心复杂性在于：**时间约束、并发依赖、安全优先级三者交织**。发射准备阶段需要多子系统并发执行以缩短周期，但这些子系统之间存在精确的依赖顺序；与此同时，来自安全系统的紧急信号必须能在任意时刻打断正在进行的操作；故障的处理也不是统一中止，而是按影响范围分级响应。

本项目以纯 asyncio Python 实现全部子系统的仿真模拟器，使控制逻辑可在无硬件环境中完整验证。实际部署时，模拟器层替换为 Tango 中间件与真实硬件的接口，上层控制逻辑保持不变。

## 2. 宏观架构

系统分为三个水平层次，自下而上：

```
┌──────────────────────────────────────────────────┐
│  Web 接口层                                       │
│  api/main.py (FastAPI)  +  static/ (HTML/JS)     │
│  SSE 实时推送 · REST 控制命令 · DAG 可视化        │
├──────────────────────────────────────────────────┤
│  控制逻辑层                                       │
│  JZGK (controller.py)                            │
│  ├── 状态机：IDLE/PREPARING/FIRING/POST/E-STOP   │
│  ├── 工作流引擎 (workflow.py)：DAG 步骤调度       │
│  └── 安全监控 (safety.py)：SafetyWatcher         │
├──────────────────────────────────────────────────┤
│  设备抽象层                                       │
│  SimulatorRegistry + 16 个子系统模拟器            │
│  统一接口：state · status · inject_fault · reset  │
└──────────────────────────────────────────────────┘
```

**层间关系的关键原则**：

- 控制逻辑层**不关心**子系统内部状态机，只调用其操作方法（如 `bb.prepare(energy)`）。设备抽象层负责内部状态转换和安全信号发射。
- 设备抽象层**不关心**发次语义，只负责自身动作的执行和故障上报。
- 控制逻辑层对 Web 接口层同样不感知。可观测性（步骤状态、阶段变化）通过回调注入，控制器本身无任何 Web 依赖。

这种分层使得系统可以在没有 Web 前端的情况下独立运行（命令行模式），也可以替换任意一层而不影响其他层。

## 3. 流程模型：系统的组织核心

整个系统的设计以**一次发次的生命周期**为组织原则。理解这个流程模型是理解所有其他设计决策的前提。

### 3.1 发次状态机

控制器用形式化状态机表达发次生命周期：

```
IDLE ──────► PREPARING ──────► FIRING ──────► POST ──────► IDLE
               │                  │              │
               └──────────────────┴──────────────┘
                              任意状态
                                  │
                                  ▼
                           EMERGENCY_STOP ────► IDLE
```

每个状态对应明确的物理语义：

| 状态 | 含义 |
|------|------|
| `IDLE` | 系统空闲，等待下一发次指令 |
| `PREPARING` | A 阶段：光链初始化、真空建立、靶瞄定位 |
| `FIRING` | B 阶段：充电、触发、激光发射 |
| `POST` | C 阶段：数据采集、吹扫、模型校准 |
| `EMERGENCY_STOP` | 中止：安全归零所有激活子系统 |

状态转换由 `_VALID_TRANSITIONS` 冻结集合形式化约束，非法转换在运行时立即抛出异常。这不是防御性编程，而是架构保证：状态机的非法转换意味着控制逻辑存在 bug，应立即暴露而非静默失败。

### 3.2 发次数据流

发次数据以两个对象携带：

**ShotRecipe**（输入）：操作员意图的编码，包含泵浦能量、充电电压、晶体角度、靶标编号、各阶段超时等参数。这是一次发次的"配方"。

**ShotRecord**（输出）：执行结果的完整记录，包含 UV 能量、X 射线信号、中子计数、γ 信号、各阶段耗时、每步耗时、模型校准版本。成功或失败的发次都会生成完整记录，失败时附带中止原因。

这两个对象贯穿整个发次执行，以参数和局部变量的形式在三个阶段之间流动，不依赖任何全局状态。这使得并发运行多发次（如果将来需要）在数据层面是安全的。

### 3.3 三阶段结构的依据

发次被分为 A/B/C 三个阶段，边界并非任意划分，而是基于物理上不可逆操作的分界点：

- **A→B 边界**：光链已就绪、真空已建立、区域已清场。越过此边界意味着能量系统开始充电，是进入高危状态的门槛。
- **B→C 边界**：激光已发射，能量已释放。越过此边界后操作转为纯读取和复原，风险性质完全不同。

每个阶段之间都有显式的安全检查点（`safety.check()`），防止上一阶段结束后至下一阶段开始前积累的安全信号被忽略。

## 4. 控制执行：流程的机械化

### 4.1 声明式调度：DAG 工作流引擎

每个阶段内部的逻辑不写成顺序代码，而是以 **DAG（有向无环图）** 声明步骤之间的依赖关系，由工作流引擎负责调度执行。每个步骤声明三件事：做什么（action）、依赖谁（deps）、失败时怎么处理（hard/soft）。引擎负责一件事：找出当前所有依赖已满足的步骤，并发执行，等待完成后推进到下一批。

这种设计将"做什么"与"怎么调度"彻底分离。控制器只需要描述物理依赖关系，并发机会由引擎自动提取，无需手动协调。每个步骤只是一个无参数的函数，不知道自己在哪个阶段、与哪些步骤并发，也不感知安全逻辑。

引擎的失败策略是**快速失败**：某个硬故障步骤失败时，立即取消同批其余任务，不等待它们自然结束，然后将 `WorkflowAborted` 向上抛出。这与"等待所有失败"的容错写法相反，体现"发现问题立即中止"的原则。

步骤还携带一个 `compensate` 字段，声明中止时的反向动作。引擎在 action 开始执行前就将步骤记录为"已启动"，保证即使步骤在执行中被取消，补偿记录也不会丢失。中止时，引擎对所有已启动步骤执行补偿，并发进行，单项失败不阻塞其他——这与执行阶段的快速失败策略相反：补偿的目标是尽量多地完成安全归零。

### 4.2 A 阶段：发射准备

A 阶段将系统从静止推进到"具备发射能力"的门槛，核心工作是光链初始化、真空建立、靶瞄定位，以及安全确认。

```
zk_monitor（启动真空后台监控）
│
├─┬─────────────────────────────────── [并发 10 步] ──────┐
│ ├── zzz_out      ZZY 种子源出光
│ ├── epj_out      EPJ 二倍频注入
│ ├── yf_wakeup    YF 预放唤醒（热机）
│ ├── dcf_align    DCF 主放迭代准直
│ ├── jzt_load     JZT 加载发次配方
│ ├── bb_prepare   BB 泵浦准备
│ ├── bm_pos       BM 靶预定位
│ ├── zk_evacuate  ZK 靶室抽真空
│ ├── wlzd_setup   WLZD 诊断配置        [软故障]
│ └── cly_setup    CLY 采样配置         [软故障]
│
├── fault_check   全量故障检查（硬/软故障分级）
├── s3_check      真空告警梯级决策
├── dcf_confirm   DCF 最终就绪确认
├── aq_clear      人员清场
└── aq_lockdown   区域联锁激活
```

这 10 个步骤操作相互独立的子系统，可以并发执行。真空监控（`zk_monitor`）是例外，必须先行启动，因为 S3 信号可能在任意并发步骤执行期间到达，监控必须已在运行。

并发完成后，`fault_check` 统一核查所有子系统的故障状态。故障检查故意放在所有初始化之后，而非每步完成后立即检查——子系统完成动作后状态才稳定，统一检查看到的是最终状态，而非短暂的过渡状态。

尾部的四个步骤必须串行：故障确认、真空评估、准直确认、清场、联锁，每一步都是进入下一步的物理前提，是 A 阶段向 B 阶段移交控制权前的层层核验。

诊断（`wlzd_setup`）和采样（`cly_setup`）配置为软故障，失败只记录警告。这两类设备不影响激光发射的物理可行性，在它们故障时宁可执行一次无诊断数据的发次，也不浪费靶丸和能量。

### 4.3 B 阶段：发射

B 阶段是发次风险最高的阶段，从能量充电到激光触发，全程有不可逆操作。

```
jzt_single（JZT 加载单次触发配方）
│
├─┬──────────────────── [并发 4 步] ──────────────────────┐
│ ├── bb_charge    BB 泵浦充电
│ ├── kg_charge    KG 开关充电
│ ├── plz_crystal  PLZ 晶体调姿
│ └── wlzd_arm     WLZD 探测器就绪
│
├── fault_check   充电故障检查
├── safety_chk    安全信号同步检查
├── s3_check      真空告警决策
│
├── bb_trigger    BB 泵浦放电触发
├── kg_trigger    KG 开关触发（严格在 BB 之后）
│
├─┬─── [并发] ───────────────────────────────────────────┐
│ ├── yf_pump     YF 接收泵浦能量
│ └── dcf_fire    DCF 接收泵浦并完成放大
│
├── plz_uv        PLZ 输出紫外
├── cly_sample    CLY 采样开始
├── jzt_arm → jzt_fire    JZT 就绪并广播触发脉冲
└── capture_uv    记录 UV 能量
```

JZT 配方加载先于充电，使触发配方在充电期间已就绪，充电完成后可立即进入触发序列。

充电完成后，`safety_chk` 是一个主动安全检查点，在进入不可逆的触发序列之前做最后确认。触发序列严格串行：BB 先放电产生泵浦光，YF 和 DCF 各自接收能量完成放大（两者并发），PLZ 接收放大后的基频光转换为紫外，最后 JZT 广播触发脉冲。这条链路的顺序是物理固定的，颠倒任何一步都会破坏能量传递。

### 4.4 C 阶段：后处理

C 阶段在发次完成后执行，风险性质与前两个阶段完全不同——从高风险操作转为读取、复原与学习。

```
wlzd_acquire（探测器采集触发后信号）
│
├─┬─── [并发] ───────────────────────────────────────────┐
│ ├── cly_read    CLY 读取激光参数
│ └── wlzd_read   WLZD 读取物理信号（X射线/中子/γ）
│
├── record_data   写入 ShotRecord
│
├── lk_purge_on → yf_purge → lk_purge_off   YF 冷气吹扫
│
└── mx_calibrate  MX 用本次数据更新预测模型
```

数据读取之前先触发 `wlzd_acquire`，作用是通知探测器从缓冲区读取本次触发后的信号，而不是历史数据。CLY 和 WLZD 是独立测量系统，并发读取，汇入同一个 `record_data` 步骤（fork-join 模式）。

吹扫序列三步不可并发——必须先开冷气、再吹扫光学元件、再关冷气，这是物理操作的直接约束。

`mx_calibrate` 居于最末，用完整的本次测量数据更新下次发次的预测模型。这是聚变装置"每发次学习"的软件表达：系统在每次实验后修正自身，下次发次的配方参数将基于这次的校准结果。

### 4.5 安全守卫（safety.guard）

安全监控是一项横切关注点：S1/S2 信号可以在发次执行的任意时刻到达，与当前步骤无关。`guard()` 将这个关注点完全外置于工作流引擎，引擎本身不感知安全逻辑。

每个阶段协程被 `guard()` 包裹后，阶段执行和紧急事件监听作为两个独立任务并发运行，采用"任一完成即返回"策略：阶段正常完成则继续，紧急事件先触发则向阶段注入取消信号。`CancelledError` 从当前 await 点向上穿透整个调用栈，工作流引擎感知到取消后清理内部任务并继续传播，最终由 `guard()` 转换为 `ShotAborted`。

两个 `guard()` 调用之间有短暂的阶段切换间隙，由 `safety.check()` 同步核查覆盖：

```
guard(_phase_a)  →  safety.check()  →  guard(_phase_b)  →  safety.check()  →  guard(_phase_c)
└── 执行期间覆盖    └── 切换间隙覆盖
```

信号传播路径单向无环：子系统发出信号 → SafetyWatcher 设置紧急事件 → guard 取消阶段协程 → start_shot 捕获 ShotAborted → 状态机进入 EMERGENCY_STOP → entry action 自动触发补偿。进入 EMERGENCY_STOP 状态自动触发补偿，无论通过哪条代码路径到达该状态，补偿都不会被遗漏。

### 4.6 补偿动作：与流程定义共址

补偿逻辑声明在每个 Step 的 `compensate` 字段中，与激活动作紧邻，流程定义即补偿规格。引擎在 action 开始执行前就记录步骤已启动，消除了取消信号在激活与记录之间打断的竞态窗口。

中止时，引擎对所有已启动步骤执行声明的补偿动作，并发运行，单项失败不阻塞其他。AQ 联锁的补偿是特例：若 AQ 因 S1 信号进入故障状态，软件保留该状态而不自动解除联锁，必须由操作员人工确认清场后手动复位——这是物理安全对软件行为的约束，不能绕过。

## 5. 错误处理体系

系统的错误处理是分层的，不同来源、不同严重程度的错误有不同的处理路径。

### 5.1 故障分级：硬故障与软故障

在阶段内部，`_check_faults()` 区分两类子系统故障：

**硬故障**：影响发次安全或物理可行性的故障（光链断裂、真空不足、能源故障）。触发后立即抛出 `ShotAborted`，当前批次其他步骤被 cancel。

**软故障**：诊断和测量类子系统的故障（物理诊断配置失败、测量取样失败）。这些子系统不影响激光发射本身，故障只记录警告，发次继续执行——本发次只是缺少部分诊断数据，物理实验仍然有效。

软故障的设计体现了对业务语义的精确建模：在聚变实验中，宁可执行一次无诊断数据的发次，也不能因诊断设备故障而浪费宝贵的靶丸和能量。

### 5.2 S3 真空告警的梯级决策

S3（真空泄漏）信号是软故障与硬故障之间的灰色地带，因此有独立的决策逻辑：

```
无 S3 告警        → 继续
气压 > 阈值×100   → 严重泄漏，升级为硬故障，中止
气压 > 阈值       → 轻度泄漏，记录警告，继续（操作员应关注）
```

这种分级处理避免了两种错误：过于宽松（忽视严重泄漏危及实验安全）和过于严格（因轻微漏气中止每次发次）。

### 5.3 异常转换链

工作流引擎和控制器之间使用不同的异常类型，需要转换：

- 工作流引擎抛出 `WorkflowAborted`，包含失败步骤名和原始异常
- 控制器需要 `ShotAborted`，包含中止原因分类（`AbortReason`）

转换由 `_abort_from_workflow()` 完成：若原始异常已是 `ShotAborted`（如 `_check_faults` 直接抛出的），则直接透传；否则包装为 `SUBSYSTEM_FAULT` 类型。这保留了异常的原始语义，避免在转换过程中丢失中止原因。

### 5.4 超时的三个层次

系统在三个层次设有超时保护：

1. **单步超时**（`Step.timeout`）：单个步骤的最长等待时间，目前未在默认配方中启用，可按需配置。
2. **阶段超时**（`ShotRecipe.phase_a/b/c_timeout`）：`asyncio.wait_for` 包裹整个阶段协程，保证发次不会永久卡住。阶段超时触发后被捕获并转换为 `ShotAborted(TIMEOUT)`。
3. **安全守卫**：虽然不是超时，但 `safety.guard()` 提供了等效的"阶段中断"能力，应对硬件层面的不可预期中断。

### 5.5 补偿的执行语义

补偿阶段故意采用与执行阶段相反的策略：`asyncio.gather(return_exceptions=True)` 并发执行所有补偿，单项失败只记录日志、不阻塞其他项。执行阶段"发现问题立即中止"，补偿阶段"尽量多地完成安全归零"——两者的目标性质不同，对应的失败策略也相反。

## 6. 可观测性与 Web 接口

### 6.1 观测与控制的分离

Web 接口层以两种通信模式对应不同需求：

- **SSE（Server-Sent Events）**：服务器→浏览器的单向推送，用于实时状态更新。选择 SSE 而非 WebSocket，是因为 UI 到服务器的控制指令天然是请求-响应模式（REST 更合适），不需要双向流。
- **REST**：浏览器→服务器的控制命令（发次入队、紧急停止、故障注入、配置调整）。

控制器对 Web 层没有直接依赖，通过三类回调实现解耦：
- `on_phase_change`：状态机转换事件
- `set_step_callbacks(on_start, on_done)`：步骤级事件
- `registry.on_state_changed / on_safety`：子系统状态和安全事件

`api/main.py` 的启动逻辑将这些回调连接到 `EventBroadcaster`，后者负责向所有已连接的 SSE 客户端扇出（fan-out）事件。

### 6.2 DAG 实时可视化

前端的 DAG 可视化不是一个纯展示组件，而是实时反映控制执行状态的仪表板。

后端在 `GET /api/workflow/{phase}` 静态返回每个阶段的步骤列表和依赖关系；前端用 dagre.js 计算布局后用原生 SVG 渲染。布局计算只在阶段切换时执行一次，步骤状态变化（`step_start`/`step_done` SSE 事件）直接更新节点颜色和图标，不触发重新布局，保证视觉稳定性。

颜色编码直接映射控制语义：灰色（待执行）→ 橙色脉冲（运行中）→ 绿色（成功）→ 红色（失败）→ 深橙色（软故障）。软故障节点在角落额外标记橙点，与完全失败节点视觉区分。

### 6.3 发次队列与历史

发次队列（`ShotQueue`）是 JZGK 控制器之上的一层调度，实现多发次顺序执行和排队管理。JZGK 控制器本身不管理队列，只负责执行单次发次。队列层通过无限消费循环（`run_loop()`）驱动 JZGK，并在每次发次完成后广播 `shot_complete` 事件更新历史记录面板。

取消排队中的发次不能从 `asyncio.Queue` 中物理删除（该数据结构无删除 API），而是在配方对象上设置 `_cancelled` 标记，由消费循环在出队时检查跳过。这是对 asyncio 约束的最小代价绕过，未引入额外的同步开销。

### 6.4 仿真速度的运行时调整

`sim_speed` 是所有模拟器共享的时间压缩因子，决定 `_delay(seconds)` 的实际等待时间。它通过 `POST /api/config` 在运行时调整，实现方式是遍历注册表中所有模拟器实例并更新其 `sim_speed` 属性，无需重建任何对象。

调整速度不影响任何控制逻辑，因为所有时间敏感代码都通过 `_delay()` 间接使用 `sim_speed`，控制器层的超时（`phase_a_timeout` 等）以真实时间计，与仿真速度无关。这允许操作员在 Web 界面上快速测试多发次流程，然后切换到慢速仔细观察单发次细节。
