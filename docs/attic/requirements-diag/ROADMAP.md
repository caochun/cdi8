# 物理实验诊断系统集中控制软件——开发路线图

## 总体策略

先纵向打通一条从总控指令到设备动作的完整链路，再横向铺开各功能模块。

```
M1 Tango设备抽象层
 └→ M2 数据模型与设备接入
     └→ M3 流程引擎
         ├→ M4 总控接口对接
         │   └→ M5 安全联锁
         │       └→ M6 实验参数配置与报告  ← 最小可运行系统
         ├→ M7 运行监控
         ├→ M8 数据分析与离线测试
         ├→ M9 可视化与大屏
         ├→ M10 智能运维
         └→ M11 VR与系统管理
```

M1–M6 是"能跑起来"的最小闭环，M7–M11 可并行迭代。

---

## M1: Tango 设备抽象层

**目标**：验证 Tango 9.5 + GBase 8s + Ubuntu 26.04 环境下与真实诊断设备的通信能力，建立设备抽象基类。

**不涉及需求编号**（基础设施层）

**关键交付物**：
- Tango 开发环境搭建（Python/Java binding）
- 用一台真实设备（建议示波器）跑通最小闭环：注册 Device Server → 读属性 → 写属性 → 调用 Command → 获取返回值
- 设备抽象基类设计：统一的参数读写、指令调用、状态订阅、超时处理、异常处理接口
- 7 类设备的参数集和指令集定义（CMOS相机、示波器、分幅/条纹相机、高压电源、标定模块、运动控制模块、光电管高压电源）
- Tango 事件订阅机制验证（后续状态监测依赖）

**依赖**：硬件环境就绪、至少一台真实设备可用、设备厂商提供 Tango Device Server

**技术风险**：
- GBase 8s 与 Tango 的事务协调（设备注册需要数据库和 Tango 双写一致）
- 设备掉线/重连的实际行为
- Tango 事件订阅在工控网络环境下的可靠性
- Python/Java 混合调用 Tango 的兼容性

---

## M2: 数据模型与设备接入

**目标**：建立诊断单元/设备/系统/分组的三层+横切数据模型，实现设备接入与 Tango 服务自动注册。

**需求编号**：001、002、003、004

**关键交付物**：
- 数据库表结构设计（诊断单元、诊断设备、诊断系统、诊断分组，及其关联关系）
- 诊断单元接入（001）：新增单元时同步注册 Tango 服务，失败回滚；预设参数配置；远程控制（调用单控界面）
- 诊断设备管理（002）：设备与单元的一对多关联维护
- 诊断系统管理（003）：系统与设备的一对多关联维护
- 诊断分组管理（004）：横切逻辑分组，支持群控
- 权限隔离机制（谁创建谁管理）
- 操作日志记录基础框架

**依赖**：M1 设备抽象层

**技术风险**：
- 不同设备类型的参数集差异大，数据模型需要足够灵活（多态 or 动态 schema）
- Tango 服务注册与数据库写入的事务一致性

---

## M3: 流程引擎

**目标**：实现可视化流程编辑和自动化流程执行，这是整个系统的业务核心。

**需求编号**：007、008

**关键交付物**：
- 流程配方数据结构（DAG：节点 + 连线 + 条件表达式）
- 流程编辑器后端：节点/连线的 CRUD、参数配置（节点绑定设备分组→设备命令→设备参数）、版本管理（草稿→校核→发布）
- 流程执行引擎：加载已发布流程 → 按 DAG 拓扑序执行 → 通过 Tango 下发指令 → 等待反馈 → 自动流转
- 并行分支执行支持
- 超时机制（每个节点有超时限制）
- 异常处理与人工干预（暂停/跳过/设备取消）
- 子流程调用机制
- 流程执行日志与节点状态记录
- 用真实设备跑通一个最小流程验证（如：参数配置 → 采集 → 读取结果）

**依赖**：M2 数据模型（流程节点引用设备分组和指令）

**技术风险**：
- DAG 执行引擎的并发控制（多个并行分支同时操作不同设备）
- 流程暂停/恢复的状态持久化
- 条件表达式的解析和求值
- 长时间运行流程的可靠性（设备超时、网络抖动）

---

## M4: 总控接口对接

**目标**：实现与集中管控系统（运维任务管控组件）的双向接口，使诊断系统能嵌入装置发射流程 DAG。

**需求编号**：外部接口需求（与集中管控系统接口部分）

**关键交付物**：
- 下行接口（总控→本系统）：远程开关机、开机自检、功能检查、参数配置、发射控制（准备/采集/结束/中止）、诊断设备状态确认、诊断设备参数设置、发射后处理
- 上行接口（本系统→总控）：服务权限验证、服务权限申请、故障上报、执行结果反馈
- 订阅模式接口：系统状态反馈（selfCheckState/selfCheckStatus）、健康度反馈（healthState/healthStatus）
- 数据同步：服务标识同步（每日从总控数据库读取）
- 发次编号管理（接收总控下发的发次编号，贯穿全系统数据组织）

**依赖**：M3 流程引擎（总控指令触发内部流程执行）

**技术风险**：
- 与运维任务管控组件的权限验证机制的实际对接
- 总控下发指令与内部流程执行的映射关系
- 发射流程中止时的状态恢复

---

## M5: 安全联锁

**目标**：实现安全联锁机制，保障流程执行中的设备安全，这是流程引擎投入真实环境的前提。

**需求编号**：010

**关键交付物**：
- 真空度安全联锁：对接真空靶室分系统获取实时真空度，DIM 伸缩前/中校验
- 碰撞安全联锁：对接靶瞄准定位系统获取 DIM 搭载平台 X/Y/Z 坐标，实时距离计算
- 设备互斥矩阵：DIM/闸板阀/真空机的互斥关系校验
- 联锁事件注入流程引擎：触发时暂停当前节点，等人工确认
- 关键信号失效处理：进入安全锁定状态
- 联锁事件记录与追溯

**依赖**：M3 流程引擎 + M4 总控对接（联锁告警需上报总控）；外部依赖真空靶室分系统和靶瞄准定位系统的接口

**技术风险**：
- 实时距离计算的精度和延迟
- 联锁响应的实时性要求（必须在设备动作造成损害前中止）
- 与外部分系统（真空靶室、靶瞄）的接口可用性

---

## M6: 实验参数配置与报告

**目标**：补全实验的"头"（参数配置+任务确认）和"尾"（实验报告），形成完整的单发次实验闭环。

**需求编号**：006、011

**关键交付物**：
- 实验参数配置（006）：接收总控下发的实验任务（只读部分）、诊断值班长配置诊断参数（可编辑部分）、参试设备树形选择与绑定、实验任务确认上报总控
- 诊断实验报告（011）：报告模板管理、数据提取填充（实验信息+设备参数+原始数据+预处理数据）、Word 格式导出

**依赖**：M4 总控对接（接收实验任务、确认上报）

**技术风险**：
- 报告模板的灵活性（不同实验类型可能需要不同模板）
- 大量图片/波形数据嵌入 Word 的性能

**里程碑意义**：M6 完成后，系统具备最小可运行能力——能接收总控任务、配置参数、执行流程、控制设备、保障安全、生成报告。

---

## M7: 运行监控

**目标**：为流程执行提供实时监控能力，包括设备状态看板、故障告警、设备手动控制。

**需求编号**：009、013、014

**关键交付物**：
- 设备控制界面编辑器（009）：画布绘制控制面板、控件绑定 Tango 属性、生成单控/群控界面、实验阶段权限申请机制
- 状态监测显示（013）：设备拓扑图（颜色编码）、实时数据看板、设备详情弹窗（参数+历史曲线+告警记录）
- 故障及告警显示（014）：三级告警（轻微/严重/紧急）、声音+弹窗、故障关联数据联动（前N分钟+后M分钟趋势图）、故障上报总控、历史追溯查询

**依赖**：M1 Tango 事件订阅（实时状态推送）、M2 数据模型

---

## M8: 实验数据分析与离线测试

**目标**：实现实验数据的多维度对比分析，以及离线环境下的设备测试和流程仿真。

**需求编号**：005、024、025

**关键交付物**：
- 实验数据分析（005）：五种对比维度（多发次/实验vs仿真/同类型单元/分组/通道）、四种分析算法（偏差/均值/求异/趋势）、图片/波形并排展示
- 单元测试（024）：单设备离线调试，调用 Tango 接口验证指令和返回值，生成测试报告
- 虚拟实验流程测试（025）：复用流程引擎，走仿真工作流引擎，数据独立存储，生成测试报告

**依赖**：M3 流程引擎（离线测试复用）、需要一定的实验数据积累（数据分析）

---

## M9: 可视化与大屏

**目标**：实现控制室大屏的显示方案编辑和实验态势集中展示。

**需求编号**：012、015、016

**关键交付物**：
- 显示方案编辑（012）：拖拽控件（图表/视频/虚拟仪表等）、绑定数据源、保存为 JSON 模板、下发大屏渲染
- 视频融合（015）：多摄像头视频+虚拟3D场景拼接、靶球内部虚拟漫游、DIM位置坐标转换、碰撞预判联动安全联锁、设备运动轨迹模拟
- 实验态势分析（016）：大屏集中展示（任务区/流程区/设备区/参数区/视频融合区/采集信息区）

**依赖**：M5 安全联锁（视频融合联动）、M7 状态监测（数据源）；外部依赖靶场摄像头系统、3D 模型资产

**技术风险**：
- 视频融合的实时性和画面质量
- 3D 场景渲染性能
- 大屏硬件适配

---

## M10: 智能运维

**目标**：建立设备全生命周期的健康管理和智能运维能力。

**需求编号**：019、020、021、022、023

**关键交付物**：
- 健康评估管理（019）：加权求和算法、100分制、A-E五级、指标可配置、系统级健康度上报总控
- 故障库管理（020）：自动采集+人工录入、29项故障信息、自动统计基础故障概率
- 故障树建模（021）：可视化树形拓扑、与门/或门逻辑、自底向上概率计算、预警机制
- 设备寿命预测（022）：五类输入数据、预测模型、剩余寿命/更换时间/故障原因输出
- 智能运维（023）：本地 RAG 知识库构建（OCR+切片+向量化）、AI 问答（检索+Rerank+LLM）

**依赖**：需要较长时间的实验数据和故障数据积累；M7 故障告警（故障数据来源）

**技术风险**：
- 工控局域网物理隔离环境下的 LLM 部署（需本地化模型）
- 故障树概率计算的准确性（依赖故障数据质量）
- 寿命预测模型的可靠性（需要足够的历史数据）

---

## M11: VR 与系统管理

**目标**：补全 VR 展示和系统基础管理能力。

**需求编号**：017、018、026、027、028

**关键交付物**：
- 维修态势 VR（017）：3D 故障定位+虚拟拆装+维修建议方案
- VR 培训（018）：3D 动画流程培训+步骤切换+培训记录
- 资源管理（026）：组织机构→用户→角色→权限四级架构、三类管理角色、双人作业机制
- 接口管理（027）：Tango 接口仪表盘、状态同步、权限分配、调用历史、依赖关系图谱
- 日志管理（028）：五级日志、分类管理、清理归档、防篡改

**依赖**：VR 依赖 3D 模型资产和 VR 硬件；系统管理（权限/日志）实际上贯穿所有里程碑，应渐进完善

**说明**：系统管理中的权限和日志是横切关注点。基础的权限隔离和操作日志在 M2 就需要，但完整的四级权限架构、审计管理、日志防篡改等可以在 M11 集中完善。

| 数据库命名规范 | M2 | 持续 |
