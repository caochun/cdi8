### 步骤 3：设计开发优先级探讨

**用户指令**：如果你来设计开发这个系统，你会先做什么

**核心观点**：第一步做**接口契约定义**，而不是 UI、数据库或流程引擎。

理由：
- 系统涉及 14 个分系统并行开发，接口不清楚是最大风险
- 接口契约是所有团队并行开发的解耦点，一旦各方签字确认，集中管控可用 mock 对接，各分系统可独立自测
- 契约内容需细化到：Tango device name、command 参数类型、返回值语义、超时上限、失败处理策略

**紧跟着做**：基于契约立刻构建**仿真器**（mock 全部 14 个分系统的 Tango 接口，支持模拟正常/超时/失败），让流程控制的开发和测试完全不被硬件进度卡住。代码库中已有仿真器相关提交，方向正确。

### 步骤 8：开发 16 个分系统仿真器

**用户指令**：按计划进行下一步（开发仿真器）

**执行过程**：在 `simulator/` 目录下构建 PyTango 仿真器，结构如下：

```
simulator/
├── requirements.txt          # pytango>=9.4.0
├── run_simulator.py          # 主入口，启动全部 Device Server
├── test_simulator.py         # 无数据库验证脚本（MultiDeviceTestContext）
└── devices/
    ├── __init__.py           # 导出 ALL_CLASSES 列表
    ├── base.py               # SimBase 基类
    └── <16 个分系统 Device>  # seed_source.py ... model_calibration.py
```

**核心设计**：
- `SimBase` 基类提供 `_exec()` 和 `_exec_json()`，统一处理 JSON 输入解析、模式切换、延迟模拟
- 每个 Device 继承 SimBase，只需声明各自的 Tango Commands（`@command` 装饰器）
- 支持 5 种运行模式，可通过 `SetMode` 命令在运行时切换：

| 模式 | 行为 |
|------|------|
| normal | 成功，200ms 延迟 |
| slow | 成功，5s 延迟（模拟设备繁忙） |
| fail | 返回 0（失败） |
| no_perm | 返回 2（无服务权限） |
| timeout | 永久挂起（模拟超时场景） |

**验证**：所有 .py 文件通过 AST 语法检查。安装 pytango 后可运行 `python test_simulator.py` 做无数据库集成验证。

### 步骤 10：流程控制引擎设计讨论

**用户指令**：先谈一谈你对流程控制引擎的设计想法吧

**设计结论**（5 个维度）：

1. **执行模型**：`asyncio + ThreadPoolExecutor`。PyTango `DeviceProxy` 调用为阻塞 I/O，用 `loop.run_in_executor()` 包装后交给 `asyncio.gather()` 并行执行同一 Stage 内的多个 Step，不引入 Celery 等外部依赖。

2. **DAG 表示**：YAML 配方文件（每阶段一个文件），对应需求文档「流程配方编辑」概念。引擎只负责解析+执行，流程变更只改 YAML，不改代码。每条 Step 声明：`device`（Tango 路径）、`command`、`timeout`、`critical`（是否熔断触发器）。

3. **引擎结构**：
   - `RecipeLoader`：加载/校验 YAML
   - `StageExecutor`：并行执行单个 Stage 内所有 Step
   - `StepRunner`：执行单个 Tango 调用（含超时、重试）
   - `FlowState`：内存状态机（PENDING / RUNNING / SUCCESS / FAILED）
   - `CircuitBreaker`：熔断逻辑

4. **熔断策略**：三级——单步超时返回失败状态码；critical 步骤失败取消同 Stage 其余步骤并上抛 `StageFailed`；阶段级熔断停止后续所有 Stage。non-critical 步骤失败只记录告警不阻断。

5. **决策点（用户待确认）**：
   - 配方持久化：YAML 文件（v1） vs 数据库
   - 流程状态存储：内存（v1） vs SQLite/PostgreSQL
   - 三阶段是连续执行 vs 阶段间人工确认

**v1 选择**：YAML 文件 + 内存状态，三阶段由引擎连续执行（无人工门控）。

### 步骤 11：开发流程控制引擎 v1

**用户指令**：好，先按你的想法开发第一个版本

**执行过程**：在 `flow_engine/` 目录下构建引擎，结构如下：

```
flow_engine/
├── __init__.py
├── requirements.txt       # pyyaml + pytango
├── engine.py              # FlowEngine（run_all / run_phase）
├── executor.py            # StageExecutor + StepRunner（asyncio + ThreadPool）
├── loader.py              # RecipeLoader（YAML 校验）
├── state.py               # FlowState / PhaseResult / StageResult / StepResult
├── test_engine.py         # 无 Tango 依赖测试脚本
└── recipes/
    ├── phase1_prep.yaml   # 发射准备阶段（11 stage，最大 7 路并行）
    ├── phase2_firing.yaml # 发射阶段（5 stage）
    └── phase3_post.yaml   # 发射后处理阶段（8 stage）
```

**核心设计**：
- YAML 配方文件定义 DAG，每条 Step 声明 `device`、`command`、`timeout`、`critical`
- `asyncio.gather` + `ThreadPoolExecutor` 并行执行同一 Stage 内的多个 Step
- critical 步骤失败 → 阶段熔断，后续阶段不再执行
- non-critical 步骤失败 → 记录 SKIPPED，流程继续
- 测试脚本通过 `unittest.mock.patch` 替换 `_call_tango`，无需 PyTango 即可验证引擎逻辑

**测试结果**：`2/2 tests passed`
- 正常模式：三阶段 24 个 Stage、52 个 Step 全部 SUCCESS
- 熔断模式（T05 注入失败）：Phase 1 熔断，Phase 2/3 不执行，熔断原因正确上报

### 步骤 12：实验任务全周期业务框架探讨

**用户指令**：要不开始考虑实验任务全周期业务的实现框架？

**框架思路**：以「实验任务」为核心实体，围绕其状态机组织整个系统。

```
实验任务状态机：
DRAFT → APPROVED → SCHEDULED → READY → EXECUTING → COMPLETED / FAILED
```

全周期链路（流程引擎只覆盖「发射执行」一段）：
**需求申报 → 供光时间表 → 排程 → 日计划发布 → 参数反演 → 发射执行 → 任务跟踪 → 发射报告**

**技术选型**：FastAPI（原生 async，与流程引擎天然对齐）+ PostgreSQL + 单体架构（v1）

**待决策的三个权衡点**：
1. **参数反演放哪里**：业务层算好传入引擎，还是引擎 T02 步骤调外部服务？
2. **发射报告**：`FlowState.summary()` 直接存库，还是专门报告生成模块？
3. **日计划粒度**：发次间衔接（后处理结束 → 下一发准备）是引擎自动循环，还是值班长手动触发每发？

**本步骤结论**：框架方向明确，用户确认目标为先完成 MVP，待确定 MVP 范围后进入实现。

### 步骤 13：确定 MVP 范围
