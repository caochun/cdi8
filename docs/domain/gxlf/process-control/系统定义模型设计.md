# GXLF 设施系统定义模型

本模型依据[集中管控系统控制流程业务说明](集中管控系统控制流程业务说明.md)定义 GXLF 实验设施的静态结构。它回答“设施由什么组成、这些组成部分如何连接、每类设备能提供什么能力、哪些结构约束必须始终成立”。

权威源文件是 [`gxlf-facility.system-definition.xml`](../../../../examples/gxlf/system/gxlf-facility.system-definition.xml)。它不描述设备当前状态，也不描述某一次发射。

系统定义之后的两个模型分别是[设施实例绑定](../../../../examples/gxlf/system/gxlf-facility-binding.xml)和[设施状态投影](../../../../examples/gxlf/system/gxlf-facility-state-projection.xml)。前者把逻辑实例、束线和外部接口交给运行环境解析；后者把设备观测组合成正交设施事实和可复用放行谓词。

## 模型边界

| 模型 | 职责 |
|---|---|
| 系统定义模型 | 分系统、设备类型、实例数量、资源、接口、拓扑和系统不变量 |
| 设备 SCXML | 单台设备的状态、动作准入、本地反馈和故障 |
| 设施状态投影 | 根据设备实时观测计算当前设施事实，例如设备是否上电、联锁是否成立 |
| 发次运行模型 | 发次编号、配方、阶段、动作证据、采集历史和正式发射结果 |
| BPMN | 某次实验的操作编排、并行、等待、人工确认和异常出口 |

系统定义模型不包含 `initialized`、`configured`、`emissionConfirmed` 等发次阶段。这些名称描述的是一次实验的运行过程，不能成为设施的永久结构状态。

集中管控系统本身也作为系统上下文中的 `central-control` 节点建模。它拥有命令下发、服务预约、健康监测、参数读取、数据接收和联锁协调端口，但它的流程行为仍由 BPMN 和运行时实现，不把 BPMN 节点复制进系统定义。

## 设施组成

业务说明中列出的 14 类控制分系统以及数量如下：

| 类型 | 数量 | 角色 |
|---|---:|---|
| 种子源 | 1 | 光源 |
| 二倍频 | 1 | 可选光源 |
| 再生与双程放大 | 10 | 预放 |
| 多程放大 | 60 | 束线放大和准直 |
| 泵浦 | 1 | 泵浦、充电和触发 |
| 测量取样 | 60 | 束线测量 |
| 频率转换 | 60 | 晶体位姿 |
| 靶瞄准定位 | 1 | 靶和光束定位 |
| 真空靶室 | 1 | 真空观测和保持 |
| 物理实验诊断 | 1 | 诊断采集和后处理 |
| 集中同步 | 60 | 束线同步和触发 |
| 开关驱动源 | 1 | 开关充电和触发 |
| 冷却 | 1 | 片放吹扫 |
| 控制环境 | 1 | 清场、警示和环境联锁 |

屏蔽门控制和人员计数属于建安工程外部接口。它们参与安全联锁，但不是激光设备类型。风淋门在业务说明中仍标为待定，因此模型保留接口并标记为未决范围。

## 拓扑和约束

`topology` 是一张有名字的关系图，例如光路、测量、同步、控制和安全联锁图；`connection` 是图中的具体连接边，表达源端口、目标端口、关系类型、方向和实例分配；`mapping` 只表达实例数量和资源分配。三者不能互相替代。

例如，`seed.optical-out -> preamp.optical-in` 是光路连接，`synchronization.timing-out -> pump.trigger-in` 是同步连接，`interlock-controller.stop-out -> all-components.command-in` 是广播式安全连接。当前 XML 已经把这些连接作为每个拓扑路径中的显式元素。

- 设施拥有 60 条束线。
- 8 条束线可以在种子源和二倍频之间选择，其他束线只能使用种子源。
- 10 套预放覆盖 60 条束线，每套服务 6 条束线。
- 多程放大、测量取样、频率转换和集中同步按束线一一绑定。
- 泵浦、开关驱动源、靶瞄、真空、诊断和控制环境属于全局设施资源。
- 安全联锁至少需要屏蔽门锁闭、人员计数归零和靶室真空稳定三个输入。
- 同步触发具有固定时间窗口：`T0` 接收触发，`T+3s` 完成泵浦和开关触发准备，`T+5s` 完成正式触发。
- 同一实验资源预约不能被多个发次同时占用。

业务说明中提到的服务健康、心跳、参数服务、实验数据入库和资源预约也作为接口或端口声明。具体参数、响应码、同步/异步调用方式和超时值由动作契约定义，不重复写入系统结构模型。

这些规则属于设施的结构和安全约束。它们不能被某个 BPMN 节点的名称替代，也不能由设备 SCXML 单独表达。

## 与 SysML 的关系

在工程设计视图中，可以把本模型映射为 SysML：

- `block` / `part` 表示设施、分系统和设备实例；
- `port` 表示 Tango、HTTP、同步、真空和安全接口；
- `connect` 表示光路、同步和联锁连接；
- `requirement` / `constraint` 表示数量、束线覆盖和安全约束。

仓库中的 XML 是运行时可校验的受限表达，不要求运行时直接解析完整 SysML。后续如果使用 SysML 工具，应从 SysML 设计模型生成这份 XML，而不是让 BPMN 直接读取 SysML 文件。

## 当前实现范围

服务端已经能够校验 `system-definition/v1`、`facility-binding/v1` 和 `facility-state/v1` XML，包括端口、中央控制节点、显式连接、实例绑定、观测、事实和未决项；工作台也会预览这些模型。设备状态机仍从 `examples/gxlf/components/` 加载；发次运行模型和 BPMN 对设施事实的能力引用将在下一步单独实现。
