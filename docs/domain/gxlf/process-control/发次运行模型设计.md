# GXLF 发次运行模型

发次运行模型描述“一次实验发生了什么”，与设施系统定义和设施状态投影分开：

| 模型 | 内容 |
|---|---|
| 系统定义 | 设施的设备、端口、拓扑、能力和不变量 |
| 设施状态投影 | 当前设备观测组合出的设施事实和放行谓词 |
| 发次运行模型 | 本发身份、配方、资源选择、阶段、证据、数据引用和结果 |
| BPMN | 本发操作如何编排 |

权威结构见 [`shot-run.schema.json`](../../../../contracts/shot-run.schema.json)。

发次记录至少包含：

- `run_id` 和 `shot_id`；
- 设施定义、实例绑定和状态投影的版本引用；
- 配方引用及版本；
- 束线选择和本发光源选择；
- 资源预约租约；
- 本发阶段；
- 设施事实、设备命令、服务健康、联锁和同步时序证据；
- 参数、诊断、测量和触发结果的数据引用；
- 失败或取消原因。

`stage` 是本发的生命周期，不能当作设施的现实状态。设备当前是否满足条件仍从设施状态投影读取；本发是否执行过某个动作、该动作是否属于当前发次，则通过 `evidence` 记录。

BPMN 后续应同时使用两类放行信息：

```text
设施事实：interlockEstablished、allServicesHealthy、triggerAllowed
本发证据：parameters_received、charge-result、trigger-result
```

设备恢复到正常状态不能自动恢复已经失败的发次；设施当前状态正常也不能证明本发命令已经成功。`shot-run.schema.json` 只定义数据边界，阶段如何推进仍由 BPMN 和运行时负责。
