# GXLF 系统状态模型设计

本文依据[集中管控系统控制流程业务说明](集中管控系统控制流程业务说明.md)，按“确定系统边界 → 定义业务状态 → 声明设备事实 → 定义转换 → 关联操作流程 → 验证异常行为”构建系统状态声明。设备依据为 [`components/`](../../../../examples/gxlf/components/) 下的十四份 SCXML。

可执行声明为 [`gxlf-experiment.system.xml`](../../../../examples/gxlf/system/gxlf-experiment.system.xml)，初始化操作流程为 [`gxlf_system_initialization.bpmn20.xml`](../../../../examples/gxlf/bpmn/gxlf_system_initialization.bpmn20.xml)。两者分别表达“系统现在应当是什么”和“怎样通过操作使其成立”。

当前交付包括全生命周期的状态声明与未决证据阻断、完整实验主干的非执行业务设计，以及十四类设备初始化段的实际联动。后续正式发射和后处理尚未实现为可执行的十四类设备操作 BPMN；准备阶段已接入技术验证动作链，但采用临时联锁和真空观测假设；不能把原四组件演示流程的执行成功解释为完整系统验证通过。

主干业务设计现已补充为[非执行 BPMN](../../../../examples/gxlf/design/gxlf_experiment_backbone.bpmn20.xml)，阶段、操作、入口/持续条件、完成证据和异常去向统一见[实验主干与系统状态对应表](实验主干与系统状态对应表.md)。另有[初始化与参数下发技术验证流程](../../../../examples/gxlf/bpmn/gxlf_initialization_parameter_dispatch.bpmn20.xml)已执行接入，用于验证同一状态记录跨越 `initialized → configuring → configured`；其中参数生效判据是临时验证假设。下文“BPMN 待实现”指执行接入尚未完成，不表示没有业务设计。原谓词及未决正式发射和释放转换阻断未改变。

正常生命周期之外的异常类别、锁存记录与待实现的处置/恢复模型，见[异常场景与系统状态建模](异常场景与系统状态建模.md)；业务/安全/接口方待决策的问题整理在[异常处置规则评审清单](异常处置规则评审清单.md)。可执行模型现在会记录已观察到的设备故障、安全联锁、阶段条件失效和证据未知，并阻断普通编排；这不代表终止设备或物理安全处置已经实现。

业务名义共 259 套设备，另有屏蔽门控制和人员进出计数两个外部接口。模型通过运行时集合量化参与实例，没有把 259 或束线拓扑写死。每类一个实例的模拟用于验证十四类接口和阶段汇合，不是 259 台规模或全部束线覆盖的验收。生产参与实例清单、束线选择和设备服务预约仍需另行接入。

当前 Java 模拟环境管理器还限制最多 200 个组件实例，因此不能直接按上述名义数量创建完整环境；完整规模联调前须调整容量约束并进行负载验证。

`allComponents` 是本次运行的全部参与设备；`sourceTargets` 是本次选择的供光设备，可选种子源、二倍频或两者。选中两者时两者都须满足出光条件，不是任意一台成立即可。每类设备的自动集合也由部署服务生成。声明要求的组件缺失时拒绝运行。

### 1.2 三层职责

| 层次 | 职责 |
|---|---|
| 设备 SCXML | 本机状态、请求准入、`cond` 守卫、动作反馈、故障锁存、保护任务。 |
| 操作 BPMN | 选择参与者，安排动作次序、并行、等待、超时、失败处理，并报告业务里程碑。 |
| 系统状态声明 | 定义整体业务状态、设备事实和允许的状态转换；持续验证当前状态是否仍可信。 |

当前 Java 模拟链路是 Workbench / Flowable → Java bridge → JTango → Java 多设备进程。业务说明规定一般分系统采用 Tango，控制环境采用 HTTP，门控接口待定；将控制环境作为 Tango 模拟设备仅用于统一联调，并不意味着真实 HTTP 接口已接入。

运行业务只识别当前声明和当前参与设备，不把“模型版本”建成业务状态。工作台发布记录和部署 XML 是开发、复现和审计资料。`state_revision` 用于设备观测顺序校验，也不是业务版本。

## 第二步：定义业务状态

系统状态不是每个 BPMN 节点的复制。只保留会改变整体运行含义或证据要求的阶段；阶段内部的具体先后仍在操作模型中表达。

| 状态 | 业务含义与主要事实 |
|---|---|
| `uninitialized` | 尚未全部初始化；允许各设备从未检查到上电检查完成。 |
| `powered` | 全体上电检查通过；允许逐台功能检查完成。上电检查不执行物理上电。 |
| `initialized` | 全体参与实例功能检查通过。 |
| `configuring` | 本发参数接收中；允许已接收和未接收设备并存。 |
| `configured` | 本发参数已接收；当前技术验证切片以十二类可参数化设备的终态和真空/环境当前可观测状态作为临时判据，生产发次关联证据仍需补齐。 |
| `preparing` | 参数后各准备支路展开，并建立安全联锁。 |
| `interlockedPreparation` | 完整联锁应已成立，后续准备继续；现有两项事实不足以放行。 |
| `prepared` | 所有准备链路完成的 AND 里程碑，本身不执行控制动作。 |
| `formalPreparation` | 正式发射前置操作展开，持续保持联锁、选定光源及参数有效。 |
| `chargeReady` | 全部发射充电前置条件成立。 |
| `charging` | 泵浦充电启动或进行中；其他发射前置设备保持就绪。 |
| `charged` | 本机已确认实际充电完成，不能以动作成功或 `chargingActive` 替代。 |
| `countdown` | 正式同步时序阶段；必须另有本发 T0、T+3s、T+5s 证据。 |
| `emissionConfirmed` | 正式发射结果确认；最终结果口径未确定前禁止进入。 |
| `postprocessing` | 并行采集、待机、收靶、预电离和保护吹扫。 |
| `postprocessed` | 后处理应已完成；保护吹扫可以仍独立进行。 |
| `released` | 满足业务释放条件后解除环境联锁；泵浦、预放等后处理完成事实继续保持，保护任务仍单独保持。 |

业务阶段之外，运行时另存完整性 `valid / violated / unknown`。联锁失效时不强行跳到一个“正常结束”阶段，而是保留失效发生时的阶段、原因、时间和设备证据。设备后来恢复不会自动恢复本次运行。

本声明是一次初始化至现场释放的骨架，尚未定义跨发次重入、预电离子周期、40 分钟保护吹扫与下一发最后 15 分钟重叠的完整并行状态模型。

## 第三步：声明设备事实

### 3.1 事实与条件作用范围

命名 `fact` 是多个设备谓词的 AND，不建立另一套资格对象，也没有资格建立/撤销 API。`use` 只复用事实定义。谓词对集合内所有匹配组件的实例成立；同一个 `require` 的多个叶状态是 OR，`states` 与 `outerStates` 也是 OR；多个 `require` 和多个 `use` 为 AND。

```xml
<fact id="selectedLightStable" label="全部所选光源稳定出光">
  <require collection="sourceTargets" component="seed shg" states="stableEmission" />
</fact>

<state id="powered" label="全体上电已确认 / 功能检查中">
  <use fact="powerMaintained" />
  <use fact="powerChecked" scope="entry" />
</state>
```

默认 `scope="invariant"` 要求状态存续期间保持；`scope="entry"` 只在进入状态时核验。进入 `powered` 时必须所有上电检查完成，但后续功能检查会把叶状态从 `powerOnOk` 变为 `functionReady`，不能因为正常进展就认定上电事实失效。因此持续条件接受这两种叶状态，进入条件严格要求上电完成。转换进入前的中间事件只由源状态条件评判，不能倒用目标状态条件。

即使所有设备都达到某些目标叶状态，也不会自动推进业务阶段；需要 BPMN 显式报告允许的转换。反过来，BPMN 汇合也不能绕过设备事实核验。

### 3.2 当前关键事实映射

| 事实 | 来自设备的主要证据 |
|---|---|
| `powerChecked` | 种子源 `powerOnChecked`，其余十三类 `powerOnOk`，全体实例 AND。 |
| `functionChecked` | 种子源 `qualified`，其余十三类 `functionReady`，全体实例 AND。 |
| `configurationAccepted` | 十二类 `configured / parameterOk`；真空和控制环境仅有可观测状态。 |
| `knownInterlock` | 控制环境 `interlockEstablished` AND 靶室 `vacuumStable`，明确不是完整联锁。 |
| `selectedLightStable` | 全部所选光源 `stableEmission`。 |
| `preparationHardware` | 预放 `fineLoopOk`、多程 `shotReady`、测量 `motionPrepared`、靶瞄 `shotReady`、诊断 `deviceConfirmed`、泵浦 `emissionPrepared`、同步 `repeatConfigured`、吹扫已停止。 |
| `formalHardware` | 诊断 `acquisitionReady`、晶体 `poseSet`、泵浦 `chargePrepared`、能量计 `energyMeterCleared`、同步 `singleConfigured`、测量 `measurementPrepared`、开关 `chargeComplete`、多程和靶瞄 `shotReady`、吹扫已停止。 |
| `chargingHardware` | 泵浦 `chargePrepared / chargingActive / chargeComplete`，覆盖正常充电过渡。 |
| `chargeSupportMaintained` | 充电过程中，除泵浦外的正式发射前置事实继续保持。 |
| `chargedHardware` | 只接受泵浦 `chargeComplete`。 |
| `countdownHardware` | 泵浦和开关允许由充电完成走向 `triggerReady`，同步由 `singleConfigured` 到 `triggerSent`；其他就绪条件保持。 |
| `postprocessingObserved` | 采集、待机、计数核验等当前结果；尚不能证明本发完整历史链路。 |

`configuredDevices` 是阶段内允许的设备演进范围，单独使用不能证明所有准备操作已完成。具体完成状态还要叠加 `preparationHardware`、`formalHardware` 等严格谓词。多程当前模型用 `collimation` 和 `enter_shot` 区分准直与打靶，整体准备完成采用 `shotReady`，同时覆盖业务说明中准直后的打靶运动准备要求。

### 3.3 不能凭当前叶状态推定的事实

以下缺口直接对应转换的 `blocked` 原因，不能通过把演示条件全部置 true 消除：

1. 真空的本发参数接收；设备接收结果与本发编号/阶段的关联。真空没有参数控制动作，不能擅自新增“已配置”状态。
2. 独立门锁、人员计数、多程钛泵真空；风淋门范围。控制环境“联锁（不含真空度）”不能替代这些接口。
3. 同步的预放/测量两个重频、两个单次通道。单个 `repeatConfigured` 或 `singleConfigured` 不能证明两个通道均完成。
4. 警灯、警示音乐、结束播报的独立状态；当前组件没有全部对应事实。
5. 本发 T0 受理、T+3s 瞬间准备和 T+5s 正式触发的时钟与实际反馈。
6. 正式发射最终判据：同步总体结果是否足够，还是还须泵浦实际触发结果。
7. 本发“已采集后待机”的历史与预电离完成；当前 `standbyReady` 不能证明先前采集过。
8. 保护吹扫实际持续时间和跨发次重叠。当前只验证 `purgeActive` 不被流程终止、待机或关机动作清除，准直应等待其停止。

## 第四步：定义转换

| 转换 | 来源 → 目标 | 操作关联与当前放行情况 |
|---|---|---|
| `powerChecksVerified` | `uninitialized → powered` | 十四类上电检查全体完成，已接入初始化 BPMN。 |
| `functionChecksVerified` | `powered → initialized` | 十四类功能检查全体完成，已接入初始化 BPMN。 |
| `beginConfiguration` | `initialized → configuring` | 参数动作前切换到过渡阶段；声明允许，操作 BPMN 待实现。 |
| `configurationVerified` | `configuring → configured` | 技术验证切片已接入；生产发次参数版本、真空参数接收和发次关联证据仍未达到现场放行标准。 |
| `beginPreparation` | `configured → preparing` | 启动准备支路；BPMN 待实现。 |
| `safetyVerified` | `preparing → interlockedPreparation` | 技术验证已接入控制环境清场/锁门和真空当前状态假设；生产仍需完整安全联锁证据。 |
| `preparationVerified` | `interlockedPreparation → prepared` | 技术验证已接入现有设备动作链；生产仍需双通道重频及完整准备证据。 |
| `beginFormalPreparation` | `prepared → formalPreparation` | 正式发射前置支路展开；BPMN 待实现。 |
| `chargePrerequisitesVerified` | `formalPreparation → chargeReady` | **阻断**：单次通道、警灯音乐证据缺失。 |
| `beginCharging` | `chargeReady → charging` | 必须在充电动作前报告，允许设备正常离开精确入口状态。 |
| `chargingVerified` | `charging → charged` | 等待泵浦本机实际完成反馈，不把 `charge` 成功当成充电完成。 |
| `countdownStarted` | `charged → countdown` | **阻断**：本发时序证据缺失。 |
| `emissionVerified` | `countdown → emissionConfirmed` | **阻断**：最终完成口径待确认。 |
| `beginPostprocessing` | `emissionConfirmed → postprocessing` | 启动采集等支路；BPMN 待实现。 |
| `postprocessingVerified` | `postprocessing → postprocessed` | **阻断**：本发历史链路与预电离证据缺失。 |
| `releaseVerified` | `postprocessed → released` | **阻断**：开门汇合策略及警示解除/播报证据待确认。 |

`blocked` 是 Java 运行时实际拒绝的字段，`operation` 是业务关联说明，不执行其中的文本。请求被阻断时不记录成功转换，也不把仍然有效的源状态标成设备违例。即使删去 `blocked`，也不等于补齐了设备事实或完成了现场联锁设计。

从初始状态沿未阻断转换最多可到 `configuring`；目前操作流程只报告到 `initialized`。系统模型测试固定这一可达性边界，防止未决证据被意外放行。

## 第五步：关联操作流程

新增初始化流程按以下顺序执行：

```mermaid
flowchart LR
  A[建立系统状态观察] --> B[全部参与实例并行上电检查]
  B --> C[全体汇合并报告 powered]
  C --> D[全部参与实例并行功能检查]
  D --> E[全体汇合并报告 initialized]
  E --> F[记录初始化成功]
```

两个设备任务都直接使用 `allComponents` 多实例。上电阶段要求 `uninitialized`，功能阶段要求 `powered`，并引用 `act:actionContract`。单设备在什么状态下能执行检查，继续由 SCXML 请求迁移判断；BPMN 不复制十四份动作准入状态表。任务按组件分别核验完成叶状态。

任一动作失败、命令超时、流程超时或手动停止，都走失败出口，保留未决设备动作。系统状态失效由通用推进器中断流程，不能以 Flowable 结束推定物理设备已停止。

在工作台中选择入口 **GXLF 十四类设备初始化**，选择十四类组件模型并设置实例数，然后应用模拟环境、开始调试。若要后续引用供光事实，还应配置 `sourceTargets`。更换 SCXML 后须重新应用环境，使设备持有当前模型；不会自动覆盖用户已有环境或草稿。

旧四组件流程文件已移除；当前运行入口统一使用十四类设备初始化和技术验证流程。设备状态机仍可单独用于 SCXML 动作和状态验证。

后续操作建模必须先细化两个问题：预电离是后处理中的独立子周期，不能直接复用正式发射阶段的全部谓词；保护吹扫与下一发准备有重叠，不能用单个线性阶段的结束自动清除保护任务。当前后处理状态允许范围仅为初步映射，不作为这两个子模型的验收。

## 第六步：验证异常行为

| 场景 | 自动验证与期望 |
|---|---|
| 十四份设备模型 | Java / Apache SCXML 实际加载，上电、功能检查通过；十二类参数动作通过。 |
| 反馈重复与冲突 | 十四类设备的重复模拟反馈返回首次结果，不改变设备快照；改写反馈结果被拒绝。 |
| 请求与实际完成分离 | 泵浦 `charge` 成功仅到 `chargingActive`，过早触发准备被拒；实际充电完成反馈后才接受。 |
| 保护任务不被清除 | 吹扫中报告流程终止后仍保持 `purgeActive`，待机/中止复位/关机均拒绝。 |
| 真空失效 | 复压立即离开真空保持，不能用错误反馈直接跳回保持。 |
| 联锁异常锁存 | 触发后解锁不清除异常，恢复到 `resetReady` 后还须重新功能检查。 |
| 进入条件与持续条件 | 进入前的正常中间事件不违反目标条件，进入后的正常推进不受一次性条件约束。 |
| 同设备多个条件 | 同一条事件必须同时满足该设备全部 AND 条件，短暂失效后恢复仍锁存。 |
| 证据无法确认 | 缺少来源/修订、来源更换、修订倒退、断连、事件缺口、服务事件代次变化均为 `unknown`。 |
| 参与者不完整 | 缺失、空集合、无匹配实例均不放行；真实 Tango E2E 验证缺一类模型时拒绝启动。 |
