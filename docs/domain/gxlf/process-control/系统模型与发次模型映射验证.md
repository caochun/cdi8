# 系统定义模型与发次模型边界

本文保留上一阶段“设施状态与发次状态拆分”的讨论记录。当前已经进一步明确：设施的静态结构、设施实时状态和发次运行状态必须分别建模。

当前设施定义见[系统定义模型设计](系统定义模型设计.md)和 [`gxlf-facility.system-definition.xml`](../../../../examples/gxlf/system/gxlf-facility.system-definition.xml)。该 XML 只描述 14 类分系统、60 条束线、设备能力、接口、拓扑和不变量。

| 模型 | 例子 | 内容 |
|---|---|---|
| 系统定义模型 | `gxlf-facility.system-definition.xml` | 设施是什么 |
| 设备模型 | `components/*.scxml` | 单台设备如何工作 |
| 设施状态投影 | 待实现 | 设施当前有哪些现实事实 |
| 发次运行模型 | 待实现 | 某一次实验进行到哪里、产生了哪些证据 |
| BPMN | `bpmn/*.bpmn20.xml` | 如何编排一次实验 |

`powered`、`ready`、`interlocked`、`charged` 等名称如果继续使用，应属于设施状态投影的派生事实；`initialized`、`configured`、`emissionConfirmed`、`postprocessed` 则属于发次运行状态。它们都不应再写入设施结构定义文件。

下一步是先实现设施状态投影，再定义发次运行模型和 BPMN 的双向放行约束。旧的综合状态 XML 不恢复。
