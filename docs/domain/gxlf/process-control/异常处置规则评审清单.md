# GXLF 异常处置规则评审清单

本文把[异常场景与系统状态建模](异常场景与系统状态建模.md)中的待确认事项拆成可评审的决策和验收证据。业务说明中的原词句是需求依据；“未决期间系统行为”是软件侧的保守建议，不代替现场应急规程，也不授权系统自动执行未经确认的物理动作。

本文当前处于原型验证阶段，以下“原型暂定评审”由模型实现者依据现有业务说明和设备状态机提出，用于验证状态表达与软件阻断行为，不代表现场安全审批或生产运行授权。后续现场规程、接口反馈契约或风险评估与此不符时，应优先修订原型结论和实现。

正式评审仍建议包含业务流程负责人、安全负责人、对应设备负责人和接口负责人。每项结论需记录决策责任角色、依据、设备反馈契约、失败时人工处置人及验收场景。

## 原型暂定评审结论

| ID | 原型暂定规则 | 原型实现边界 | 重新评审触发条件 |
|---|---|---|---|
| D1 | “紧急触发”与“紧急停车”视为不同且语义未闭合的操作；异常期间不自动触发、不自动重发。 | 记录倒计时阶段、设备反馈和未知结果；只阻断正常后续编排。 | 明确紧急触发的物理效果、授权、时窗和权威完成证据后。 |
| D2 | 命令接受/成功不等于停充或能量已安全释放；超时、断连、结果冲突均为未知。 | 不自动下发停充、泄放或复位，不据此释放资源或进入下一发。 | 泵浦提供经确认的动作互锁和能量安全终态反馈后。 |
| D3 | 已确认的全局联锁事件应优先于普通流程，锁存并阻断普通命令；同时保留触发时阶段和各设备独立结果。 | 联锁触发可以作为系统异常事实；“终止所有分系统、解锁门、开启警报”仅作为待确认处置，不宣称已执行或已安全。 | 明确覆盖设备清单、各类终止语义、门控/警报接口和失败接管规则后。 |
| D4 | 多实例的部分无响应必须单独保留，不以整体流程停止或其他设备成功推断其已停止。 | 显示各实例已知状态；通信中断或缺少反馈标为未知，阻断依赖其安全状态的正常推进。 | 确认超时、升级角色、人工签收和事故关闭契约后。 |
| D5 | 解锁、开门请求、门实际打开、允许人员进入是四个不同状态。 | 没有独立物理反馈时显示未知，不由解锁回执推导门已开或允许进入。 | 门控、人员计数和风淋门硬联锁范围得到确认后。 |
| D6 | 正式发射结果区分成功、失败、部分成功和未知；同步命令结果不能单独代表全部设备物理结果。 | 结果不完整或相互冲突时保留 `outcome unknown`，不推断未发射，也不跳过必要采集。 | 明确同步、泵浦、开关及诊断证据组合和冲突裁决规则后。 |
| D7 | 后处理支路、预电离和吹扫分别追踪；流程分支结束不等于持续设备任务结束。 | 吹扫状态未知时阻断依赖吹扫完成的操作；门开启汇合规则继续受阻。 | 明确失败支路收尾、开门条件、吹扫跨发次归属和异常处置后。 |
| D8 | 本发参与设备集合固定，全体 AND；不因单台失败自动缩小集合或移除联锁覆盖。 | 保留部分失败实例和当前发次范围，禁止自动降级继续。 | 对具体设备组、工艺和风险影响形成批准的降级策略后。 |
| D9 | 设备复位或进入 `resetReady` 不清除系统层已锁存异常，也不恢复旧发次。 | 事故/异常记录保持锁存；新发次须显式启动。 | 接入身份授权、复核、事故关闭和新发授权流程后。 |

这些规则只定义软件如何记录、分类和阻断，不定义设备应如何进入物理安全状态。尤其 D3 中的门解锁、警灯警报、停充、泄放等动作，原型不会自动执行。

## P0：必须先确认的安全行为

### D1：倒计时异常时的“紧急触发”

- **现有依据**：业务说明称倒计时 5 秒内发生异常，或同步触发未能触发时，通过按钮向同步系统下发 `紧急触发`，由同步完成触发。
- **需要决定**：`紧急触发` 的物理效果究竟是什么；是否可能直接触发激光/泵浦/开关；适用的故障类型、允许时窗、授权角色、禁止条件、超时后的处理，以及它与“紧急停车”的关系。要分别说明“同步未受理”“倒计时已开始但 T+3 准备未完成”“T+5 未确认”时的规则。
- **闭环证据**：同步命令受理/拒绝、倒计时阶段与时钟来源、泵浦和开关准备最终状态、同步实际输出结果；若该操作可能触发物理发射，还需定义关联设备实际动作反馈和结果矛盾时的权威判据。
- **未决期间建议**：系统不得把“紧急停车”自动映射成 `紧急触发`，不得自动重发该命令。模型将该事件保留为高优先级、待授权处置；界面应醒目标出原始业务术语歧义。
- **责任角色**：安全负责人 + 同步/泵浦/开关设备负责人 + 业务流程负责人。

### D2：主发及预电离充电的紧急停充/紧急泄放

- **现有依据**：充电过程中突发异常时，向泵浦发送 `紧急停充` 并等待结果；充电完成后未能触发时，发送 `紧急泄放` 并等待泄放结果。主发与预电离均可能涉及泵浦充电。
- **需要决定**：两种命令的适用设备状态、互斥关系、能否重复、命令先后及是否可被普通流程取消；各自成功后的物理终态和失败/拒绝/超时/失联时的现场规程。要明确“命令成功”与“能量已安全释放”的区分。
- **闭环证据**：命令受理、泵浦活动任务结束、充电/能量状态的权威测量值或设备完成事件、数据来源及时间戳；反馈冲突或不可读时的独立核验方式。
- **未决期间建议**：保留 `charging`、`charged` 或 `unknown` 的相位证据，不能由工作流停止推断停充/泄放完成；禁止自动进入普通复位、下一发或设备资源释放。
- **责任角色**：泵浦设备负责人 + 安全负责人 + 业务流程负责人。

### D3：全局安全联锁触发后的终止策略

- **现有依据**：联锁范围包括屏蔽门、人员、钛泵/靶室真空度，风淋门待确认；人员被困、真空异常、重大安全隐患等可触发。触发后要求向所有流程中的分系统发送流程终止指令、解除屏蔽门锁定并触发警灯警报。
- **需要决定**：哪些设备/服务属于“所有分系统”；每类设备的终止命令究竟是停止编排、停止当前任务、停光、停充、泄放还是继续保护；高能动作、运动设备及吹扫任务的差异；门解锁/警报命令与设备终止请求的并行关系；哪类失败需要现场人工接管。
- **闭环证据**：逐实例记录终止请求已发送、已受理、动作已结束、物理安全状态已确认四个不同结果；门锁状态、实际门状态、警报状态和持续保护任务也各自有状态反馈。
- **未决期间建议**：联锁事件在系统状态中锁存并抢占普通流程；不得报告“全部终止完成”，除非策略要求的每个参与者均已核验。未响应项保持 `unknown/manualRecoveryRequired`，不释放运行资源。
- **责任角色**：安全负责人 + 全部分系统设备负责人 + 控制平台负责人。

### D4：部分设备无响应或终止未确认时的升级

- **现有依据**：多实例数量可达 10/60；业务要求设备服务监控及命令超时，但没有定义终止确认的聚合口径和人工升级流程。
- **需要决定**：确认粒度是服务、设备实例、束线还是本发参与集合；超时阈值来源；未确认设备的升级接收角色/渠道；资源、门禁和后续发次是否持续锁定；如何结束或移交事故。
- **闭环证据**：参与设备清单及稳定实例 ID、命令 ID、各实例响应截止时间、重试/核验记录、未决设备清单、人工接管及签收记录。
- **未决期间建议**：不得将多实例任务的“流程结束”视为全体设备停止；未决设备保留独立活动项，继续禁止依赖这些设备安全状态的转换。
- **责任角色**：平台值班/运行负责人 + 设备负责人 + 安全负责人。

### D5：屏蔽门解锁、开门与人员进入的边界

- **现有依据**：联锁触发后要求解除屏蔽门锁定；正常流程末尾有开门节点，但其汇合策略、接口和时长待确认，门节点还关联人员计数归零。
- **需要决定**：分别定义“解除锁定”“开门请求”“门实际打开”“允许人员进入”；各自的请求条件、反馈接口、操作权限和顺序。明确人员计数归零是在实验开始前、开门前还是两个时点都要求；明确风淋门是否是硬联锁。
- **闭环证据**：门锁、门扇位置、门控服务健康、人员动态清单/计数的独立观测；控制命令回执不可替代物理位置反馈。
- **未决期间建议**：系统只显示各项分别已确认/未知，不因“解锁成功”提示“门已开”或“现场可进入”；正常释放转换继续阻断。
- **责任角色**：安防/门控接口负责人 + 安全负责人 + 业务流程负责人。

## P1：决定流程失败、结果与恢复语义

### D6：正式发射结果的权威判据

- **现有依据**：T0 开始同步倒计时，T+3 完成泵浦和开关触发准备，T+5 同步完成触发；文档提出同步总体成功与泵浦触发结果哪个作为正式完成判据待确认。
- **需要决定**：同步、泵浦、开关及束线结果的组合规则；成功、失败、部分成功、结果未知如何分类；结果冲突时以何设备/测量为准；结果未知时哪些后处理必须运行。
- **闭环证据**：按发次/阶段/束线关联的同步输出、泵浦实际触发、开关实际放电和采集结果，含设备来源、时间及最终判定依据。
- **未决期间建议**：保持 `emissionOutcomeUnknown`，不将它当作未发射或已成功；继续保留必要的结果采集和设备处置待决项。
- **责任角色**：业务流程负责人 + 同步/泵浦/开关设备负责人 + 实验诊断负责人。

### D7：后处理失败、预电离失败与吹扫跨发次

- **现有依据**：正式发射后多条采集/待机/收靶/预电离/开关待机链路并行；屏蔽门开门是否等所有链路待确认；40 分钟吹扫期间可在结束前 15 分钟进入下一发准备。
- **需要决定**：每条支路失败后哪些动作仍必须完成；哪些失败阻止开门/结束；主发后处理与预电离分别如何终止/收尾；吹扫归属哪一发、跨发期间谁监控、设备/资源如何预约、吹扫异常时下发什么措施。
- **闭环证据**：每条后处理动作本发关联的完成反馈；吹扫持续状态和最终停止反馈；门控等待所依据的已完成支路清单。
- **未决期间建议**：不因 BPMN 子流程结束清除 `purgeActive`；吹扫状态未知时不放行依赖“吹扫停止”的准直；门开启策略保持未放行。
- **责任角色**：后处理业务负责人 + 冷却/泵浦/门控设备负责人 + 安全负责人。

### D8：多实例部分失败时是否允许降级继续

- **现有依据**：初始化明文要求所有参与组件全部通过；准备完成为 AND 汇合。其他 10/60 台设备动作按束线调用，但未定义故障实例能否隔离后继续。
- **需要决定**：按每种动作指定原子范围（全系统、束线组、单实例）；允许隔离的实例清单和依据；隔离对光路、计量、同步、安全联锁及结果判据的影响；剩余实例集合如何重新核验。
- **闭环证据**：本发选择集合、拓扑映射、故障实例与隔离批准、重新计算后的前置条件及结果覆盖范围。
- **未决期间建议**：保持全体参与实例 AND；不自动缩小本发集合、不把失败设备从联锁覆盖范围剔除。
- **责任角色**：业务工艺负责人 + 对应设备/束线负责人 + 安全负责人。

### D9：复位、事故关闭和新发次授权

- **现有依据**：设备建模说明要求故障恢复先完成内部安全处理和物理核验，进入 `resetReady` 后重新功能检查、参数校验，旧发次不得恢复；系统层授权与审计未接入。
- **需要决定**：操作员、工程师、安全负责人各自可执行/批准的步骤；安全联锁锁存由谁清除；事故何时关闭；旧流程实例如何封存；何种核验后才可人工启动新发次。
- **闭环证据**：设备复位完成、重新功能检查、重新参数/安全证据、授权人身份与确认、旧命令/旧发次不可续跑的端到端验证。
- **未决期间建议**：设备回到 `resetReady` 不自动清除系统事故或重启流程；旧发次终态保持失败/中止，由新运行显式开始。
- **责任角色**：运行负责人 + 设备维护负责人 + 安全负责人。

## 评审结论记录

对每个决策填写：

| 字段 | 内容 |
|---|---|
| 决策 ID / 结论 | D1–D9；记录明确结论及适用阶段/设备范围。 |
| 依据 | 业务条款、现场规程、设备技术说明或经批准的风险分析。 |
| 责任角色 | 谁批准规则、谁维护接口、谁执行人工接管。 |
| 设备接口契约 | 请求事件、接受/拒绝、最终物理反馈、身份关联、时限和证据来源。 |
| 异常分支 | 失败、拒绝、超时、断连、反馈冲突分别进入何种处置状态。 |
| 验收案例 | 正常闭环、部分设备失败、结果未知、恢复后旧发次禁止续跑。 |
| 状态 | 未评审 / 已决定待实现 / 已实现待验收 / 已验收。 |

## 评审后的实现顺序

1. 先实现不依赖物理策略的事故记录与证据关联：事故 ID、阶段、来源、受影响实例、命令 ID、每实例结果及未决项。
2. 实现已有明确要求的初始化全体屏障、联锁事件锁存、系统完整性未知时阻断、终止请求与确认分离；缺少接口反馈的设备进入未确认，不伪报安全完成。
3. 对已批准的每一种处置规则分别建 BPMN 事件流程和转换 guard；安全联锁处置优先于普通失败收敛。
4. 通过 Java/Tango 集成测试覆盖部分设备失败、在途命令、事件缺口、联锁抢占、停机未确认、吹扫持续和恢复后旧发次禁止续跑。
5. 根据实际 incident 与参与者状态实现可视化；在业务决策未通过前，界面显示“待确认/受阻”，不提供可执行的物理策略选择。

正式现场评审结论形成前，继续保留[系统状态声明](../../../../examples/gxlf/system/gxlf-experiment.system.xml)中的生命周期阻断；本原型只增加异常事实的显示与编排阻断，不新增自动触发、泄放、开门或设备复位行为。
