# 系统合法状态与监督契约（概念稿）

本文把集中管控系统的“整体合法状态”定义为独立于 BPMN 流程实例的监督契约。它是架构讨论稿，不代表现场安全协议已经确认，也不代表当前运行时已经实现所有规则。

约束的逐条登记和场景验证见[系统监督约束登记表与场景转移矩阵](system-supervision-constraint-register.md)。

依据是[集中管控系统控制流程业务说明](../domain/gxlf/process-control/集中管控系统控制流程业务说明.md)。该说明描述的是一条连续的发射任务生命周期；本文进一步区分：

- 设备和外部服务报告的事实；
- 由事实形成的设施状态；
- 在某个工作状态中必须持续满足的系统约束；
- BPMN 本发次如何请求能力、组织顺序和处理业务结果。

## 核心原则

流程不是整体系统合法性的所有者。流程可以表达“现在要进入发射充电”“现在要开始同步触发”这样的操作意图，但不能通过任务完成、流程取消或子流程退出，推断设备已经停止、储能已经消除或联锁已经解除。

系统监督独立于流程实例的寿命。它根据实际启用证据激活约束，根据实际解除证据结束约束；约束的保持期间可以跨越多个流程任务，也可以在流程取消后继续存在。

流程消费监督结果，而不是重新实现监督规则。监督结果至少应区分：允许、等待、阻止、失效、未知、需要人工恢复。对于门禁、联锁、储能和紧急停止相关事实，未知不能作为合法依据。

## 四层职责

| 层 | 负责的问题 | 不负责的问题 |
|---|---|---|
| 观测与适配 | 设备、控制器和外部服务报告了什么；报告是否新鲜、可信、可关联 | 决定实验下一步做什么 |
| 状态投影 | 当前每个组件处于什么状态；跨组件事实是否成立 | 保存本发流程阶段或替流程做业务选择 |
| 系统监督 | 哪些约束已生效；约束是否持续满足；何时阻止、锁存异常或允许释放 | 编排本发的业务顺序 |
| 流程编排 | 本发要执行哪些操作、按什么顺序、如何等待、失败后走哪条业务路径 | 重新计算设施固有安全约束 |

控制方向和证据方向不同：流程通过能力或动作请求向下发起意图，设备通过事件和快照向上提供证据，监督层根据证据决定该意图是否可以执行以及执行期间是否仍然合法。

## 事实、状态和约束

### 事实

事实是由当前观测或明确计算得到的判断，例如：

- `shieldDoorLocked`：屏蔽门确认锁闭；
- `personnelCountZero`：人员计数确认归零；
- `vacuumNormal`：真空输入在有效时间内正常；
- `pumpEnergyActive`：泵浦处于充电、储能或待触发状态；
- `pumpEnergyAbsent`：泵浦实际储能已经消除；
- `allFunctionReady`：当前参与集合中的组件均满足功能检查定义；
- `allParametersReceived`：本发参数已经被参与系统接收。

事实必须携带来源、观测时间、修订号或等价的顺序信息以及有效期。事实的值和事实的可信度是两个不同维度。

### 事实结果

监督计算不应只返回布尔值。至少需要以下结果：

| 结果 | 含义 |
|---|---|
| `valid` | 当前证据充分，事实成立 |
| `invalid` | 当前证据充分，事实不成立 |
| `unknown` | 缺少证据、证据过期、来源失联或存在无法消解的矛盾 |
| `stale` | 曾经成立，但超过了该事实允许的有效期 |
| `conflict` | 同一事实的有效来源给出了不能同时成立的结果 |

`stale` 和 `conflict` 可以在对外结果中归入 `unknown`，但必须保留原始原因，不能把它们静默转换成正常或安全。

### 约束

约束描述“在某种实际工作状态持续存在期间，系统必须满足什么”。约束至少包含：

| 字段 | 语义 |
|---|---|
| 标识和适用范围 | 约束是什么、适用于哪些实例或束线 |
| 启用证据 | 哪些独立观测证明约束开始适用 |
| 保持要求 | 适用期间必须持续为 `valid` 的事实或依赖 |
| 解除证据 | 哪些独立观测证明约束不再适用且可以释放 |
| 未知策略 | 关键事实未知时是阻止、锁存还是允许降级 |
| 失效策略 | 失效时需要阻止新动作、终止当前动作、发起紧急处置或人工确认 |
| 证据记录 | 启用、失效、恢复和解除所需保存的证据 |

“要求恰好成立”不能同时作为启用和解除约束的唯一条件，否则约束会在自身失效时自动消失。启用和解除必须分别由设备或控制器的实际工作状态证明。

## 约束生命周期

约束生命周期与流程任务生命周期不同。一个建议的抽象状态如下：

```text
inactive
  → activating
  → active-valid
  → active-unknown / active-violated
  → recovery-required
  → released
```

- `inactive`：没有有效启用证据，约束尚未适用。
- `activating`：已经观察到启用迹象，但建立约束所需的初始覆盖尚未完成。
- `active-valid`：约束适用，所有保持要求当前成立。
- `active-unknown`：约束适用，但无法证明要求仍然成立；受保护动作应停止推进。
- `active-violated`：已经确认要求失效；恢复为正常观测不能抹去本次失效。
- `recovery-required`：物理系统可能已经恢复，但仍需要安全退出证据、人工确认或专门恢复流程。
- `released`：已经取得解除证据；本轮约束可以结束，但异常历史仍须保留。

首次启动时如果只看到设备已经处于危险工作状态，却没有看到从安全状态进入该状态的完整证据，不能把一次健康快照当作连续安全证明。此时应进入 `activating` 或 `active-unknown`，具体策略由约束等级决定。

## 约束的三种来源

### 系统固有约束

它们由设施定义决定，是否适用取决于实际设备状态，不依赖某个 BPMN 任务是否仍在运行。例如：

- 泵浦储能期间保持联锁和服务健康；
- 开关储能期间保持联锁和服务健康；
- 光源或预放处于工作态期间保持联锁和服务健康；
- 联锁会话建立后，门禁、人员、真空和控制器状态必须持续满足要求。

流程取消不能释放系统固有约束。

### 能力执行约束

它们在某项能力执行期间适用，例如光路准直要求入射光、吹扫停止、服务健康和联锁正常。能力结束后，能力执行约束可以释放，但由能力引起的系统工作状态约束可能仍然继续存在。

### 本发附加约束

它们由本次实验选择，例如人为要求准直完成后继续保持照明五秒。它们可以由流程激活和释放，但不能代替系统固有约束，也不能降低系统固有约束的等级。

这三类约束必须在数据模型和运行时语义上分开，尤其不能把本发附加保持条件当作安全联锁的替代品。

## GXLF 核心约束初稿

以下是根据业务说明整理出的第一版监督契约。它们仍需由现场接口和业务方确认。

| 约束 | 启用证据 | 解除证据 | 保持要求 |
|---|---|---|---|
| 联锁会话 | 控制器确认已启用，且物理输入已建立 | 控制器确认释放，且解除条件成立 | 屏蔽门、人员、真空、无触发、服务健康 |
| 泵浦储能 | 泵浦进入充电、已充电或待触发状态 | 实际储能消除并得到泵浦确认 | 联锁正常、服务健康；异常后保留未决动作 |
| 开关储能 | 开关进入充电、已充电或待触发状态 | 实际储能消除并得到开关确认 | 联锁正常、服务健康 |
| 光学工作 | 光源出光、预放唤醒或相关启动动作有效 | 光源和预放均回到安全就绪，且启动动作结束 | 联锁正常、服务健康 |
| 准直操作 | 任一参与多程设备正在执行准直 | 所有参与设备确认准直动作结束 | 入射光、吹扫停止、联锁正常、服务健康 |
| 触发窗口 | 同步触发已开始倒计时 | 正式触发结果已确认，或窗口进入明确异常终止状态 | 泵浦和开关触发准备按时完成；联锁、服务和储能状态持续有效 |

其中“触发窗口”不能只由流程定时器表示。T0、T+3 秒和 T+5 秒是同步控制器与泵浦、开关之间的实时契约，流程只能记录结果和处理超时。

## 流程与监督层的交互

流程请求能力时，监督层应至少完成四步：

1. 解析本发实际参与实例和拓扑；
2. 判断能力开始条件是否有效；
3. 如果能力会激活系统约束，建立或预登记约束实例；
4. 返回允许、阻止或等待，并说明缺失的证据。

动作被接受不等于能力完成。监督层需要等待实际状态证据，能力执行期间持续重新评估保持要求。流程可以收到以下几类结果：

- `allowed`：当前可以下发动作；
- `accepted`：设备已经受理，但尚未证明物理状态完成；
- `completed`：目标状态和相关保持要求均已得到证据；
- `blocked`：当前不能开始；
- `interrupted`：执行期间约束失效或设备失联；
- `unknown`：无法判断是否仍然合法；
- `recovery-required`：需要安全处置或人工恢复。

流程取消只取消流程意图和等待，不取消监督层已经激活的系统约束。监督层必须继续观察并在取得物理解除证据后释放约束。

## 一个完整交互例子

在“发射充电”阶段：

1. 流程请求泵浦充电能力。
2. 监督层核验整体准备、单次配方、能量计、测量准备、开关状态、联锁和服务健康。
3. 允许后，动作执行层向泵浦下发充电指令。
4. 泵浦报告进入充电或储能状态后，监督层激活泵浦储能约束。
5. 流程等待泵浦实际充电完成和其他触发前置状态。
6. 倒计时中如果联锁变为未知，监督层立即撤销触发资格，并把储能约束标记为未知或失效。
7. 流程进入异常分支，但储能约束继续存在，直到泵浦确认停充、泄放或储能消除。
8. 只有释放证据成立后，监督层才允许开门或结束资源占用。

这个例子中，流程实例可以结束，而系统监督仍然必须运行。

## 对整体流程的影响

采用监督层后，BPMN 主要保留以下内容：

- 发次和阶段的业务顺序；
- 并行任务和汇合；
- 能力请求与结果等待；
- 业务超时和人工确认；
- 异常后的业务处置路径；
- 本发特有的附加保持条件。

以下内容不再由每个流程节点重复实现：

- 联锁、门禁、人员、真空和服务健康的组合判断；
- 多实例设备依赖的递归解析；
- 约束启用、持续监督、异常锁存和物理释放；
- 设备事件与快照的排序、新鲜度和来源一致性；
- 流程取消后的未决物理动作跟踪。

这并不意味着 BPMN 变成无条件的脚本。流程仍然必须等待监督层确认能力已经完成，并根据监督层的失效、未知和恢复结果选择业务路径。

## 当前需要继续确认的问题

1. 联锁控制器的启用、触发、广播终止、解除和人工确认接口分别是什么。
2. 泵浦和开关的“储能消除”有哪些可验证的实际信号。
3. 光源出光、预放工作态、准直完成和光路选通是否有独立于流程命令的现场观测。
4. 预电离是本发次的子循环，还是独立的实验操作；两种解释对应不同的资源和记录边界。
5. 片放吹扫期间开始下一发准备时，哪些实例可以重叠，哪些资源必须独占。
6. 屏蔽门打开的最终释放条件是否等待所有后处理分支完成。
7. 系统异常历史、约束实例和未决动作需要怎样持久化，才能在监督进程重启后继续保持保守语义。

在这些问题确认前，本文定义的是监督层的职责和契约形状，不把尚未确认的现场事实写成可执行安全规则。
