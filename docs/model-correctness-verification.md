# 实验流程仿真模型正确性验证思路

## 目标

验证不能只回答“代码测试是否通过”，而要回答三个问题：

1. 分系统状态机是否完整（complete）；
2. 分系统状态机是否健全（sound）；
3. 实验流程是否是分系统状态机允许行为的合法使用。

验证对象包括 Excel 转换得到的分系统模型、实验流程模型，以及两者的组合运行模型。

## 术语和基本关系

必须先定义独立于被测 YAML 的业务参考语义。参考语义来自 Excel、已确认的业务规则和明确记录的建模约定，不能直接从被测实现复制。

设：

```text
Required  业务要求必须支持的行为
Allowed   业务允许发生的行为
Model     被测状态机实际支持的行为
Flow      实验流程实际使用的行为
```

状态机正确性的基本关系是：

```text
Complete：Required ⊆ Model
Sound：   Model ⊆ Allowed
一致性：  Flow  ⊆ Model
```

这里的“行为”包括状态转移、动作结果、异常事件和恢复路径，不只是状态名称。

非法动作也必须有明确处理。例如参数未下发时执行出光，可以转入显式 `rejected`，而不是没有任何转移。显式拒绝属于 complete 的一部分，不属于 sound 违规。

## 一、分系统状态机验证

### 1. 建立参考语义

从 Excel 为每一行建立独立的规则记录：

```text
source_row
system
action 或 exception
precondition_main
precondition_current
normal_result_main
normal_result_current
exception_result_main
exception_result_current
business_state
state_definition（O 列）
state_description（L 列）
判定条件（M 列）
流程影响（N 列）
```

参考语义还要单独记录：

- Excel 明确规定的行为；
- 从文字条件提取的行为；
- 开发补充的建模约定；
- Excel 没有定义、需要业务确认的行为。

未定义项标记为 `underspecified`，不能用开发实现代替业务结论。

### 2. Complete 检查

检查状态机是否覆盖全部要求行为：

- 每个 Excel 行是否映射到动作或异常事件；
- 每个动作的允许前置状态是否可达；
- 每个动作是否有成功、失败和必要的拒绝处理；
- 故障锁定、通信异常、执行超时是否有进入路径；
- 执行中异常是否能中断当前任务；
- 异常是否有恢复、终止或人工处置出口；
- 每个已接受任务是否最终可以成功、失败、取消或超时；
- 任何可达状态和外部事件组合是否都有合法转移或显式拒绝。

Complete 需要区分：

```text
动作覆盖完整
结果覆盖完整
异常覆盖完整
恢复路径完整
事件处理完整
```

### 3. Sound 检查

检查状态机是否产生了业务不允许的行为。典型不变量包括：

```text
允许出光
    ⇒ 主状态 = 正常
    ∧ 当前状态 = 参数下发完成

主状态 = 异常
    ⇒ 业务状态 = 异常

进入正常业务状态
    ⇒ 成功回调、目标状态和必要条件全部满足

异常恢复完成
    ⇒ 原因已解除 ∧ 复位已验证 ∧ 安全位置满足 ∧ 资源已释放

旧 task_id 的反馈
    ⇒ 不能完成当前任务
```

还要检查状态字段之间是否自洽，例如：

- 失败不能仍然获得有效业务资格；
- 采集成功不能错误地退出出光；
- 复位待机、异常恢复和异常中止不能被错误合并；
- 配置失效后不能继续按旧配置出光；
- 普通关机不能隐式抢占执行中的动作。

### 4. 状态图探索

从初始状态开始，对以下事件进行有限状态空间遍历：

```text
每个动作：开始、成功、失败、错误反馈、重复反馈、迟到反馈
通用异常：故障锁定、通信异常、执行超时
状态失效：配置变化、出光失效、就绪失效
处置：异常中止、复位、恢复、关机
```

探索结果至少要检查：

- 不可达状态；
- 没有出口的非终态；
- 绕过前置条件的路径；
- 异常绕过恢复条件进入正常状态的路径；
- 任务已经结束后仍能接受其反馈的路径；
- 合法动作永久停留在执行中的路径。

验证器应输出完整反例路径，例如：

```text
参数下发成功
→ configuration_changed
→ emit.dispatch accepted
→ 违反：配置已失效仍允许出光
```

## 二、实验流程与分系统状态机一致性验证

不能只检查流程节点的动作名称是否存在。应建立组合状态：

```text
(flow_state, flow_node, subsystem_state, active_task)
```

然后沿流程调度、反馈和异常事件进行探索。

### 1. 调用一致性

流程允许下发节点时，分系统必须允许该动作：

```text
FlowEnabled(node, subsystem_state)
    ⇒ SubsystemPrecondition(node.action, subsystem_state)
```

### 2. 结果一致性

流程标记节点成功时，分系统必须完成对应成功转移：

```text
FlowNodeSucceeded(node)
    ⇒ SubsystemSuccess(node.action, evidence)
```

成功证据至少包括：

- 当前流程实例、节点和 `task_id` 匹配；
- 回调表示成功；
- 观测状态匹配动作的成功结果；
- M 列要求的条件全部满足；
- 分系统任务进入 `succeeded`。

### 3. 节点衔接一致性

对相邻流程节点检查：

```text
Post(previous_node)
    ⇒ Pre(next_node)
```

当前最小流程应验证：

```text
自检成功       ⇒ 功能检查可执行
功能检查成功   ⇒ 参数下发可执行
参数下发成功   ⇒ 出光可执行
出光成功       ⇒ 参数采集可执行
采集成功       ⇒ 待机复位可执行
待机复位成功   ⇒ 关机可执行
```

还必须插入中间事件验证状态不会被过期使用：

```text
参数下发成功
→ 配置失效
→ 出光必须被拒绝
```

### 4. 失败和异常一致性

验证以下组合行为：

- 分系统动作失败时，流程节点不能成功；
- 分系统进入异常时，流程不能放行后续节点；
- 分系统异常中止后，原流程实例不会自动恢复成功；
- 旧反馈、重复反馈和迟到反馈不能改变流程结果；
- 流程失败后，设备恢复不会自动改变已结束的流程状态。

## 三、还需要验证的性质

### Safety

不应发生的事情永远不发生，例如异常状态下出光、未复位时进入下一发、旧任务完成新任务。

### Liveness

合法动作最终会成功、失败、取消或超时；流程不会永久停留在 `executing`；异常最终有恢复或终止出口。

### 时间语义

需要验证：

- 超时前收到目标反馈可以成功；
- 超时后仍未达标必须进入执行超时；
- 超时后的迟到成功反馈不能覆盖超时结果。

### 并发和事件顺序

多个分系统加入后，需要验证并发事件、异常与成功反馈同时到达、重复下发、复位与普通动作竞争等情况。

### 状态抽象一致性

检查 Excel 的 D、H、J、K、O 列到运行时字段的映射：

```text
D 关键状态描述       → key_state_description
H/J 节点结果状态     → current_state / key_state
K 业务状态            → business_state
O 状态定义            → state_definition
```

状态定义分类本身不能直接作为流程放行信号。

## 四、验证器的实现建议

验证器应独立于状态机执行器实现，避免执行器和验证器共享同一错误。

建议输入：

```text
业务参考规则
分系统状态机模型
实验流程模型
```

建议输出：

```text
reference coverage report
state-machine completeness report
state-machine soundness report
flow/subsystem consistency report
deadlock and liveness report
counterexample traces
underspecified items
```

实现顺序：

1. 静态检查 Excel 行到动作、状态和异常的映射；
2. 检查状态字段和值域；
3. 生成有限状态图并做可达性遍历；
4. 检查不变量和非法转移；
5. 构造流程与分系统的组合状态图；
6. 检查流程节点的调用、结果和节点衔接；
7. 加入时间、重复反馈、迟到反馈和并发事件；
8. 用故意破坏模型的 mutation test 验证验证器确实能发现错误。

## 五、验收标准

在宣布模型通过验证前，应能给出：

- 每条 Excel 规则的来源和覆盖结果；
- complete 检查没有未解释的遗漏；
- sound 检查没有未解释的非法路径；
- 流程组合状态没有调用、结果或衔接不一致；
- 所有失败和异常路径都有明确结论；
- 所有时间和并发假设都有记录；
- Excel 未定义的内容明确标记为待确认，而不是默认为正确；
- 任何失败都能输出可复现的反例路径。

最终报告应把以下三种结果分开：

```text
PASS       已验证成立
FAIL       已找到反例
UNDEFINED  业务定义不足，暂时无法判定
```
